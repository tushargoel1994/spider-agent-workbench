# Hard/extra-hard question eval plan

Status: **draft, awaiting go-ahead** — nothing in this plan has been implemented yet.

## Goal

- Build a fixed benchmark of 150 Spider **train**-split questions that the
  official Spider difficulty metric (`hard`/`extra`) rates as hard or extra
  hard, spread across at least 30 distinct `db_id`s (max 5 questions per db).
- Within those 150: **at least 40% (60) extra-hard** and **at least 40% (60)
  hard** — the remaining ≤20% (30) filled from whichever bucket the
  selection naturally lands on next, with no further quota.
- Run the current agent/prompt against exactly that set and produce
  `hard_question_report.json` — a breakdown (by status, db, difficulty, SQL
  feature, guardrail hit) plus every per-question prediction — so the report
  can be read question-by-question to see where the prompt is going wrong.
- **No existing code changes** — every new file lives under
  `scripts/hard_question_eval/`, and only already-public functions from
  `loaders.py`, `eval/exact_match.py`, `eval/runner.py`, `eval/metrics.py`,
  `eval/sql_features.py`, and `logging_config.py` are reused.

## Is it possible? — yes, confirmed against real data

You were right that the codebase already computes Spider's official hardness
bucket: `eval/exact_match.py::score_exact_match()` runs the *vendored*
Spider evaluator's `Evaluator().eval_hardness()` on the parsed **gold** SQL as
a side effect of EM scoring — it doesn't need a predicted SQL to do that, so
calling it with `predicted_sql=None` gives back just the hardness bucket for
a `(db_id, gold_sql)` pair, using only existing public code.

I ran that function over the full train split once (read-only, no code
changes, ~13s) to confirm feasibility before writing this plan:

| | |
|---|---|
| Train examples with a matching local `.sqlite` | 7,000 |
| Hardness distribution | easy 1,694 / medium 2,777 / **hard 1,460** / **extra 1,068** |
| Gold SQL that failed to parse (skipped) | 1 |
| `db_id`s with ≥1 hard/extra question | 139 |
| `db_id`s with **≥5** hard/extra questions (needed for a clean 5-per-db pick) | 130 |

So a 30-db × 5-question = 150-question pool, drawn only from `db_id`s that
each have at least 5 hard/extra questions, is comfortably achievable (130
eligible db_ids available, only 30 needed).

I also simulated the per-db selection algorithm below (§`select_hard_questions.py`)
across 7 different seeds to confirm the 40%/40% hard/extra floor is reliably
hit, not just theoretically possible:

| seed | hard taken | extra taken | meets ≥60/≥60? |
|---|---|---|---|
| 42 | 75 | 75 | yes |
| 1 | 84 | 66 | yes |
| 2 | 78 | 72 | yes |
| 3 | 80 | 70 | yes |
| 4 | 81 | 69 | yes |
| 7 | 82 | 68 | yes |
| 99 | 82 | 68 | yes |

Every seed cleared both floors with room to spare (worst case 66/150 = 44%
extra), so the algorithm below doesn't need a fallback path for "couldn't hit
the target" in practice — it still raises a clear error if some future seed
or a smaller `--num-dbs` can't clear it, rather than silently shipping an
under-quota pool.

## Design: two scripts, not one, inside `scripts/hard_question_eval/`

```
scripts/hard_question_eval/
  select_hard_questions.py          # builds & freezes the 150-question pool (run once)
  hard_questions_pool.json          # generated by the above — the frozen benchmark set
  full_eval_test_hard_questions.py  # runs the agent against the frozen pool, writes the report
```

Why two scripts instead of folding selection into the eval script: you want
to compare prompt versions against each other on **the same** hard questions.
If selection re-ran (even with the same seed) inside every eval invocation,
a future change to `eval/exact_match.py`'s hardness logic or a refresh of
`train_spider.xlsx` would silently reshuffle the benchmark between runs.
Freezing the pool to a checked-in JSON file once means every future
`full_eval_test_hard_questions.py --prompt-version prompt_vN` run is
measured against the exact same 150 questions.

- `select_hard_questions.py` is meant to be run rarely (once, or again only if
  you deliberately want a new/bigger pool) — it always reads from the
  **train** split, matching `scripts/run_full_eval.py`'s existing rule
  ("Evals will always run on train and never on validation").
- `full_eval_test_hard_questions.py` **requires** `hard_questions_pool.json`
  to already exist and errors out with a clear message telling you to run
  `select_hard_questions.py` first if it doesn't — it does not silently
  regenerate the pool.

## `select_hard_questions.py`

Selection now has two layers of constraint: the structural one (≤5 questions
per db, ≥30 distinct dbs) and the composition one (≥40% hard, ≥40% extra
overall). A plain "sample 5 per db from the combined hard+extra pool"
(what the original 100-question plan did) can't guarantee the composition
floor, since a db's own hard/extra split is whatever it happens to be — so
the fill is now quota-aware: within each db, the next pick prefers whichever
of hard/extra is furthest from its global floor, and once *both* floors are
met, the remaining slots are just "whatever's left" per your "as the
questions arrive" instruction.

```
def compute_hardness_pools(hardness_levels) -> tuple[dict[db_id, list], dict[db_id, list]]:
    """Returns (hard_by_db, extra_by_db) -- kept separate, not combined,
    so the fill loop below can track each bucket's running total."""
    examples = loaders.filter_available(list(loaders.iter_examples("train")))
    hard_by_db, extra_by_db = defaultdict(list), defaultdict(list)
    for ex in examples:
        try:
            result = score_exact_match(ex.db_id, None, ex.gold_sql)
        except Exception:
            logger.warning("skipping unparseable gold SQL: db_id=%s", ex.db_id)
            continue
        if result.hardness == "hard":
            hard_by_db[ex.db_id].append(ex)
        elif result.hardness == "extra":
            extra_by_db[ex.db_id].append(ex)
    return hard_by_db, extra_by_db


def select_pool(num_dbs=30, questions_per_db=5, seed=42,
                 min_hard_fraction=0.4, min_extra_fraction=0.4):
    hard_by_db, extra_by_db = compute_hardness_pools(("hard", "extra"))
    all_dbs = set(hard_by_db) | set(extra_by_db)
    eligible = sorted(
        db for db in all_dbs
        if len(hard_by_db.get(db, [])) + len(extra_by_db.get(db, [])) >= questions_per_db
    )
    if len(eligible) < num_dbs:
        raise ValueError(f"Only {len(eligible)} db_ids have >= {questions_per_db} "
                          f"combined hard/extra questions; need {num_dbs}.")

    total_target = num_dbs * questions_per_db                    # 150
    hard_target = math.ceil(total_target * min_hard_fraction)    # 60
    extra_target = math.ceil(total_target * min_extra_fraction)  # 60

    rng = random.Random(seed)
    chosen_dbs = rng.sample(eligible, num_dbs)
    rng.shuffle(chosen_dbs)  # fill order, so which dbs get "first pick" isn't alphabetical

    selected: dict[str, list[SpiderExample]] = {}
    hard_taken = extra_taken = 0

    for db_id in chosen_dbs:
        db_hard, db_extra = list(hard_by_db.get(db_id, [])), list(extra_by_db.get(db_id, []))
        rng.shuffle(db_hard)
        rng.shuffle(db_extra)
        picks = []
        for _ in range(questions_per_db):
            need_hard = hard_taken < hard_target
            need_extra = extra_taken < extra_target
            if need_hard and need_extra:
                # further-behind bucket wins; ties go to hard
                prefer = "hard" if (hard_target - hard_taken) >= (extra_target - extra_taken) else "extra"
            elif need_hard:
                prefer = "hard"
            elif need_extra:
                prefer = "extra"
            else:
                # both floors already met -- "as the questions arrive": take
                # from whichever bucket this db has more of, no further quota
                prefer = "hard" if len(db_hard) >= len(db_extra) else "extra"

            if prefer == "hard" and db_hard:
                picks.append(db_hard.pop()); hard_taken += 1
            elif prefer == "extra" and db_extra:
                picks.append(db_extra.pop()); extra_taken += 1
            elif db_hard:
                picks.append(db_hard.pop()); hard_taken += 1
            elif db_extra:
                picks.append(db_extra.pop()); extra_taken += 1
        selected[db_id] = picks

    if hard_taken < hard_target or extra_taken < extra_target:
        raise ValueError(
            f"Selected pool doesn't meet the hardness floor: hard={hard_taken} "
            f"(need >={hard_target}), extra={extra_taken} (need >={extra_target}). "
            "Try a different --seed."
        )

    return selected, {"hard_taken": hard_taken, "extra_taken": extra_taken}
```

- CLI flags (all optional, defaulting to your numbers):
  `--num-dbs 30 --questions-per-db 5 --seed 42 --min-hard-fraction 0.4 --min-extra-fraction 0.4`.
- `try/except` around `score_exact_match` — the one genuinely-reachable parse
  failure the feasibility scan hit (1 out of 7,000) shouldn't abort the whole
  scan; this is new orchestration code scanning a large, occasionally messy
  real dataset, not a change to `eval/exact_match.py`'s own contract (which
  still assumes gold SQL parses and is free to raise when called directly on
  a single question elsewhere).
- Wanted at least 30 db_ids and exactly 5 questions each — rather than a
  variable per-db count — because it makes the resulting `hard_questions_pool.json`
  a clean, even 30×5 grid, easy to eyeball. Total is `num_dbs * questions_per_db`
  (150 by default), not a separately-tunable knob, to avoid partial-fill edge
  cases (e.g. "29 dbs get 5, one gets 3").
- The `hard_taken/extra_taken < target` check at the end is a safety net, not
  the expected path — the 7-seed simulation above always cleared both floors
  by a comfortable margin. It exists so a future `--num-dbs` much smaller than
  30, or an unlucky `--seed`, fails loudly instead of quietly shipping a pool
  that doesn't actually meet your 40%/40% requirement.
- Writes `hard_questions_pool.json`:
  ```json
  {
    "meta": {
      "seed": 42, "num_dbs": 30, "questions_per_db": 5, "total_questions": 150,
      "min_hard_fraction": 0.4, "min_extra_fraction": 0.4,
      "hardness_breakdown": {"hard": 75, "extra": 75},
      "split": "train", "generated_at": "..."
    },
    "questions": [
      {"db_id": "...", "question": "...", "gold_sql": "...", "hardness": "hard"},
      ...
    ]
  }
  ```

## `full_eval_test_hard_questions.py`

Mirrors `scripts/run_full_eval.py`'s shape (same reused collaborators,
`eval/runner.py::run_eval` + `eval/metrics.py` + `eval/sql_features.py`),
scoped to the frozen pool instead of a random sample:

1. Load `hard_questions_pool.json`; error clearly if missing.
2. `logging_config.setup_logging(phase_number="hard_question_eval")` — logs to
   `logs/phase_hard_question_eval_<timestamp>.log`, same convention as every
   other phase script.
3. `runner.run_eval(examples, prompt_version=..., num_workers=..., log_path=logs/hard_question_eval_run_<timestamp>.jsonl)`
   — same call shape `run_full_eval.py` already uses; `agent_factory` defaults
   to `agent_builder_factory.build_agent`, which already reads `MODEL_PROVIDER`
   from `.env`, so whichever provider you've got configured is what gets used.
4. Tag SQL features (`sql_features.tag_features`), build the same summaries
   `run_full_eval.py` does: `ex_summary`, `em_summary`, `feature_summary`,
   `guardrail_summary`, `operational_summary` (all via `eval/metrics.py`,
   unmodified).
5. Add one convenience view on top, specifically for prompt debugging: a
   `failures` list — just the records where `score == 0`, pulled out of
   `results` so you don't have to filter the full list by hand to see what's
   going wrong.
6. Write `results/hard_question_report.json` (matching where every other
   phase script already writes its output — `results/phase_4_result.json`
   etc. are already committed there).

Report shape:
```json
{
  "meta": {
    "input_file": "scripts/hard_question_eval/hard_questions_pool.json",
    "pool_seed": 42, "num_dbs": 30, "questions_per_db": 5, "total_questions": 150,
    "prompt_version": "prompt_v3", "num_workers": 4,
    "generated_at": "...", "log_path": "..."
  },
  "ex_summary": {...}, "em_summary": {...},
  "feature_summary": {...}, "guardrail_summary": {...}, "operational_summary": {...},
  "failures": [ {db_id, question, predicted_sql, gold_sql, status, detail, notes, ...}, ... ],
  "results": [ ...every question, same shape as run_full_eval.py's "results" ... ]
}
```

- CLI flags: `--prompt-version prompt_v3 --num-workers 4 --input-file <override> --output-file <override>`.
